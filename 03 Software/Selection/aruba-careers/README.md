# Careers page on Aruba — candidate identification (SELECTION_ARUBA_IDENTITY_001)

A two-step page, hosted on the company's **Aruba Hosting Windows** (Windows Server 2022, IIS, PHP 8.2.35), where a candidate proves an email address and is then
handed to Selection on AWS to apply for one position. No candidate account, no password.

Publication steps for the Product Owner (Italian): [ISTRUZIONI_PUBBLICAZIONE.md](ISTRUZIONI_PUBBLICAZIONE.md).

Address: `https://careers.romesflavours.com/index.php` (a third-level domain on the Aruba hosting; `romesflavours.com`
and `www` stay on Wix, untouched). FTP: the folder `careers` in the FTP root, next to Aruba's `mdb-database`.

## Flow

```text
Selection job page  ──"Verify your email to apply"──►  careers page (Aruba)  ?position=<public token>
  1. First Name, Last Name, Email ─ Receive Code ─► 5-digit code emailed from rfone@romesflavours.com (SMTP, Aruba)
  2. "Welcome, <First Name>!" ─ Verification Code ─ Confirm | Cancel
  3. right code ─► HTML form POST (body, HTTPS) of ONE signed token ─► Selection /selection/careers/verified-identity
Selection: checks signature, issuer, audience, expiry, position, single use ─► signs the candidate in for THAT
position only ─► job page (résumé upload) or, if an application is in progress, straight back to it
```

The URL never carries personal data or the code: only the position's public token (the same one in the public
job-page address). Selection's `verified-identity` endpoint takes the token from the form body only.

## Rules implemented

| Rule | Where |
|---|---|
| 5-digit code from a CSPRNG (`random_int`), new for every request | `rfc_new_code` |
| only an HMAC of the code is kept (server-side session), never logged | `rfc_hash_code`, `rfc_log` (emails and networks are pseudonymised) |
| valid 10 minutes, at most 5 attempts, a new code replaces the old one | `index.php` confirm |
| 60 s between two codes for one email, 5 codes/hour per email, 20/hour per network, 30 wrong codes/hour per network | `rfc_send_refusal`, `rfc_too_many_failures` (file counters with locks in the data folder) |
| authenticated SMTP, implicit TLS ≥ 1.2 with certificate verification, sender = authenticated mailbox | `rfc_smtp_send` (`smtps.aruba.it:465`) |
| token `RF1.<claims>.<HMAC-SHA256>`: `iss=rfone-careers-aruba`, `aud=rfone-selection`, `amr=email-code`, random `jti`, `iat`, `exp=iat+300`, `pos`, `fn`, `ln`, `em` | `rfc_issue_token` ↔ `rfone_data_store/selection/identity_handoff_service.py` |
| shared secret outside the code: `private/config.php` on Aruba, AWS Secrets Manager on Selection | `make_upload.py` |
| HTTPS only (PHP redirect, HSTS), CSP allowing forms only to the page itself and Selection, `no-store`, `noindex`, session cookie HttpOnly / Secure / SameSite=Lax | `index.php`, `web.config`, `rfc_start_session` |
| sessions, counters and logs outside the careers folder, in `<mdb-database>/rfone-careers` (Aruba: writable, never downloadable from the web; `App_Data` as second choice; `data_dir` to force a path) | `rfc_data_base` |
| URLs built from `SCRIPT_NAME` and always `…/index.php` (no dependency on `REQUEST_URI` or on IIS default documents) | `rfc_base_path`, `rfc_self` |
| TLS to `smtps.aruba.it` verified through the Windows certificate store (PHP on Windows; checked 2026-10-25 with PHP 8.2.35: valid name accepted, wrong name refused) | `rfc_smtp_connect` |

## Selection side (AWS)

- `rfone_data_store/selection/identity_handoff_service.py` — verifies the token and returns the identity for the
  verified email: the existing one if the email already applied (the same application is resumed, never
  duplicated), otherwise a new identity **without password**.
- `workspace/careers.py` — `POST /careers/verified-identity`. The first POST comes from Aruba (another site, so the
  browser sends no Selection cookie): it only re-posts the token from Selection's own page
  (`templates/careers/identity_handoff.html`), so that an RF-One login already open in the same browser is never
  replaced. The second POST accepts the token and signs the candidate in, scoped to the token's position
  (`selection_candidate_position_id` in the session): another position needs another verification.
- Switched on only when **both** `RFONE_SELECTION_CANDIDATE_IDENTITY_URL` (the careers page, https) and
  `RFONE_SELECTION_IDENTITY_HANDOFF_SECRET` (≥ 32 characters) are set. Then the job page shows only "Verify your
  email to apply" and Selection's own password registration answers 409. Without them nothing changes.
- Migration `c2b720261025` (additive): `first_name`, `last_name` on `selection_candidate_accounts`,
  `password_hash` nullable, table `selection_candidate_identity_handoffs` (the used `jti`, never the token).
- Candidate-facing status: **In Progress** = `CV_RECEIVED` (résumé saved, interview being answered, every answer
  saved at once), **Completed** = `SUBMITTED`. The existing statuses are reused, not duplicated
  (`CANDIDATE_STATUS_LABELS`).

## Test

```text
python "03 Software/Selection/test_aruba_identity_http.py"     (PHP on PATH or RFONE_TEST_PHP=<php.exe>)
```

Synthetic data only. The real PHP pages run in PHP's built-in server inside a simulated Aruba FTP root
(`careers/` next to `mdb-database/`); codes go over verified TLS to a fake SMTP server inside the test; Selection
runs as deployed on a throwaway SQLite database. 60 checks, passed on PHP 8.2.35 (Aruba's version), 7.4.33 and
8.3.36 (2026-10-25). The built-in server ignores `web.config` and answers one request at a time, so `check.php`
cannot prove `private/` closed there (it says NO, never a false OK): on IIS `check.php` verifies it.

- **Clover connector** (`rfone_data_store/technical/connectors/clover/` — relocated from `ingestion/clover/`, itself a relocation out of Tips by the now-superseded CLOVER_DATA_ACQUISITION_ARCHITECTURE_001): the ONE fetch/upsert path Tips, and eventually Server Copilot/Server Performance/Sales, all share (B — implemented and validated). Owns only Clover integration concerns (client, mapping, sync, checkpoints, idempotency) — no concept of Restaurant at all; its unit of ownership is `Location`/`Merchant`/`SourceSystem` (the existing RF-One organizational model), and a Domain caller (e.g. Tips) resolves which Location it needs via its own Restaurant -> RestaurantLocation join before calling in. Two operational modes over the same idempotent code path: **Historical Backfill** (an operator-chosen date range, triggered from Tips' "Historical Backfill" UI — explicitly NOT the normal acquisition mechanism) and **Live Sync** (`technical/connectors/clover/live_sync.py` / `clover_live_sync.py --location-id N`, a short-interval, checkpoint-advancing poll — no Clover webhook receiver/public endpoint exists in this repository today, so "seconds, not minutes" is achieved via polling, not webhooks). A single Location-scoped `IngestionRun.lock_key` guard (`CLOVER_ACQUISITION:{location_id}`) serializes both modes against the one shared SQLite file. Interruption recovery: a RUNNING run left behind by a killed/crashed process self-heals automatically on the next acquisition attempt once it exceeds a 30-minute staleness threshold, or can be checked/forced immediately via `clover_acquisition_status.py --location-id N`; a real orphaned run found stuck in `data/rfone.db` (from a manually interrupted import, pre-dating both renames) was confirmed to have left no partial/corrupt data and was recovered.

# TASK 5A — Selection Outcome + Stage + Decision History Engine: Implementation Report

## 1. What I implemented

A clean separation of three concepts Selection previously conflated inside the single `Application.workflow_status` field: **Stage** (where an Application currently is in the process — Application Received/Primary Screening/Phone Interview/In-Person Practical, with total Selezionatore freedom to move forward, backward, repeat, or skip), **Outcome** (a restaurant-configurable operational decision — Hire/Hold/Stop/Withdrawn/anything a restaurant defines — applicable at any moment, never technically irreversible), and **Decision History** (append-only Stage and Outcome history, never rewritten). A restaurant-configurable Outcome Definition wizard, a persistent Candidate Flag concept, a unified Selection Notes History spanning every Selection element, and a consolidated Decision Summary view round out the task. `Application.workflow_status` is entirely unchanged and remains fully functional.

## 2. Main files changed

New: `core/stage_model.py` (Stage vocabulary), `core/outcome_model.py` (lifecycle/future-contact/Flag vocabulary), `stage_service.py`, `outcome_service.py`, `candidate_flag_service.py`, `selection_notes_service.py`, `decision_service.py`, migration `d6a4c9e2f7b3_add_selection_5a_outcome_stage_decision.py` (+6 tables, +2 columns).
Extended: `models.py` (`Application.current_stage`/`.lifecycle_state` + `stage_transitions`/`outcome_decisions` relationships; `CandidatePerson.flags` relationship; new `ApplicationStageTransition`, `SelectionOutcomeDefinition`, `SelectionOutcomeDefinitionSnapshot`, `SelectionOutcomeDecision`, `SelectionReminder`, `CandidateFlag` models), `industry/restaurant_templates.py` (+`seed_default_selection_outcomes`), `03 Software/Selection/app.py` (+16 new routes: Stage movement, Outcome apply/reopen, Candidate Flag create/deactivate, reminder resolve, Decision Summary, Outcome Definition CRUD), `rfone_data_store/selection_validation.py` (+41 checks), `test_batch_upload.py` (+6 Flask-layer checks).
New templates: `selection_outcomes_home.html`, `decision_summary.html`. Updated: `application_detail.html` (compact Stage & Outcome section + link to Decision Summary), `base.html` (nav tab + badge CSS).

## 3. Stage model and Stage history

`core/stage_model.py` defines a fixed vocabulary (`APPLICATION_RECEIVED`, `PRIMARY_SCREENING`, `PHONE_INTERVIEW`, `IN_PERSON_PRACTICAL`) — deliberately NOT a restaurant-configurable table and NOT a state machine: no "allowed next Stage" validation exists anywhere. `stage_service.set_stage()` always inserts a new `ApplicationStageTransition` row (`previous_stage`/`new_stage`/optional `performed_by`/timestamp) and updates `Application.current_stage` as a convenience pointer only — full history is always available via `list_stage_history()`. Moving Primary Screening → Phone, Primary Screening → In-Person directly (skipping Phone), and moving backward are all exercised identically by the same unrestricted function. An optional Note on a transition is stored via the existing `ApplicationNote` mechanism (`context_type="STAGE_TRANSITION"`), never a second field.

## 4. Outcome Definition model

`SelectionOutcomeDefinition` mirrors `PrimaryScreeningCriterion`'s restaurant-configurable/active/version shape. Fields map directly to the task's own wizard questions: `lifecycle_effect` (ACTIVE/SUSPENDED/CLOSED), `is_reopenable`, `requires_note`/`requires_reason`, `reason_choices` (JSON list), `target_queue_label` (informational), `creates_reminder`/`reminder_days`, `future_contact_policy` (ALLOWED/DISCOURAGED/BLOCKED — one tri-state axis covering both "is contact allowed" and "should it be discouraged/blocked"), and `creates_candidate_flag` plus the Flag's own name/scope/operational-effect/default-reason/expiration. `industry/restaurant_templates.seed_default_selection_outcomes()` seeds ACTIVE/HIRE/HOLD/STOP/WITHDRAWN as ordinary, restaurant-editable rows — explicitly "templates, not the complete universal set" (task §4), exactly like every other seeding function in that file.

## 5. Outcome configuration wizard

`/selection-outcomes` presents one guided, conversationally-labeled form (`selection_outcomes_home.html`) rather than a raw technical form or a free-text label: "What should happen to the Application?" (with plain-language ACTIVE/SUSPENDED/CLOSED descriptions), "Should this restaurant contact the candidate again in the future?", "How seriously should this Flag be treated on a future Application?", etc. — no database terminology exposed. It is a single page (not a multi-step JS wizard, consistent with this codebase's no-JS-framework convention) but every question from task §5 is present: name, description, lifecycle effect, reopen expectation, mandatory Note/reason, reason pick-list, target queue label, reminder, future-contact policy, and Candidate Flag creation. Create/edit/activate/deactivate are all supported.

## 6. Application lifecycle behavior

Applying an Outcome sets `Application.lifecycle_state` to the Outcome snapshot's `lifecycle_effect` — always, automatically, as the one non-optional action every Outcome performs (task §6). `lifecycle_state` is a convenience pointer only; the authoritative value is always derivable from the most recent `SelectionOutcomeDecision`.

## 7. Outcome decision/history model

`SelectionOutcomeDecision` is append-only: `outcome_service.apply_outcome()` never edits or deletes a prior decision, only inserts a new one and updates the convenience pointer. `get_current_outcome_decision()` (highest-id decision for the Application) is the one current effective Outcome; `list_outcome_history()` returns the complete, chronological, never-overwritten sequence (verified directly with a 3-decision Hold → Active → Hire sequence, then a 4th reopen decision appended without disturbing the first three). Every decision pins to an immutable `SelectionOutcomeDefinitionSnapshot` (mirrors `PrimaryScreeningCriterionSnapshot`'s exact idempotent-per-version discipline) — editing the live Outcome Definition afterward never rewrites what an already-made decision meant (verified directly: editing "5A Hire"'s lifecycle effect after it was used left the historical decision's own snapshot unchanged).

## 8. Reopen/reversibility behavior

No Outcome is technically irreversible: `outcome_service.reopen_application()` is always callable regardless of the Outcome Definition's own `is_reopenable` hint (that flag is UI/policy guidance only, never a system-level block — task §7's own "no technically irreversible outcomes"). It requires selecting an Outcome whose snapshot resolves to `ACTIVE` (reopening into SUSPENDED/CLOSED would not be "reopening") and internally calls the same `apply_outcome()` path, so a reopen is simply one more history entry (flagged `is_reopen_event=True` when the Application was CLOSED immediately beforehand) — never a deletion or mutation of the prior closure decision.

## 9. Candidate Flag model and behavior

`CandidateFlag` is PERSON-level (`CandidatePerson.flags`), not Application-level, since its purpose is surfacing on a LATER Application by the same person. Fields: name, description, originating Application/Outcome Decision, reason, `scope` (INFORMATIONAL/ROLE_SPECIFIC/LOCATION_SPECIFIC/TEMPORARY/GLOBAL_WITHIN_RESTAURANT — plain fields, no separate scoping table), `role_scope`/`location_scope`, `operational_effect` (INFORMATION_ONLY/WARNING/OPERATIONAL_ACTION — capped at "requires Selezionatore attention," never automatic rejection), `note`, `start_date`/`expires_at`/`is_active`. History is preserved by never deleting a row — `deactivate_flag()`/expiration only change current state; `list_flags_for_person(active_only=False)` always returns the full history. `list_active_flags_for_application()` resolves the Application's person, filters to currently-effective (active + not expired) flags, respects restaurant scoping, and applies role-scope matching against the Application's own `target_role` — verified directly that a Flag created from one Application surfaces on a genuinely later Application by the same person (matched by email during upload), and that an expired Flag stays in history but stops appearing as active.

## 10. Notes architecture and unified Notes History

`ApplicationNote` (Task 3C-FIX) gained no new columns here (it already had `context_type`/`context_id` from Task 3D-FIX) — Stage transitions, Outcome decisions, and Candidate Flags (when they originate from a specific Application) all reuse it with new context tags (`STAGE_TRANSITION`, `OUTCOME_DECISION`, `CANDIDATE_FLAG`), never a parallel notes table. `selection_notes_service.get_selection_notes_history()` is the one unified query: it reads every `ApplicationNote` for the Application (covering Application/Stage/Outcome/Primary-Screening-Run/Criterion-Evaluation/Candidate-Flag contexts) and additionally surfaces Task 4A/4B's own pre-existing note fields (`PhoneInterviewPlan.notes`, `PhoneInterviewQuestionInstance.selezionatore_note`, `InPersonInterviewPlan.notes`, `AssessmentItemInstance.selezionatore_note` — left completely untouched) into the same chronological list, each entry carrying a context label, Stage where known, author where known, and timestamp.

## 11. Existing workflow-status compatibility

`Application.workflow_status`/`workflow_status_reason`/`workflow_status_updated_at` and `application_service.set_workflow_status()` are **entirely unchanged** — every existing route, test, and the Task 4A `phone_interview_service.record_post_interview_decision()` call site that writes it still work exactly as before (re-verified: the full pre-5A suite still passes at 265/265 before Task 5A's own 41 new checks are added). No bidirectional sync exists between `workflow_status` and the new `current_stage`/`lifecycle_state`/Outcome Decision History — deliberately, to avoid inventing a second, possibly-contradicting translation layer. Instead: `current_stage`/`lifecycle_state` are populated going forward by the NEW, explicit Stage/Outcome actions (`stage_service.set_stage`/`outcome_service.apply_outcome`), while `workflow_status` remains available, unchanged, for any code that already depends on it. A brand-new Application starts at `current_stage=APPLICATION_RECEIVED`/`lifecycle_state=ACTIVE` regardless of `workflow_status`, which independently still defaults to `NEW`. This is a parallel-coexistence bridge, not a migration of meaning — documented here rather than silently assumed, per the task's own instruction.

## 12. Decision/Application UI

`application_detail.html` gained a compact "Stage & Outcome" card (current Stage/Outcome/lifecycle badges, active Flags, a link to the full Decision Summary) immediately after the existing Workflow Status card — available regardless of what Stage the Application has reached (task §31/§32, no forced linear process). `/applications/<id>/decision` (`decision_summary.html`) is the consolidated Decision Summary (task §23): candidate identity, Original CV ↗, current Stage/Outcome/lifecycle, Primary Screening summary, evidence broken into strongest/weaker/conflicting/unresolved, trainable gaps (from existing `Requirement.trainability`), active Hard Disqualifiers, important Signals, active Candidate Flags (with create/deactivate controls), Outcome history, Stage history, Stage-movement and Outcome-application controls, open follow-up reminders, and — at the very BOTTOM of the page, per task §22's explicit UI requirement — the full Selection Notes History. A discursive, non-numeric current-summary paragraph (`decision_service.generate_current_summary_text`) supports HIRE without a separate mandatory prose justification; it states what the evidence shows and never issues or implies a recommendation.

## 14. Known limitations directly relevant to Task 5A

- `workflow_status` and the new Stage/Outcome model are NOT reconciled retroactively for Applications that already existed before this migration — a pre-existing Application simply starts at the new fields' defaults (`APPLICATION_RECEIVED`/`ACTIVE`) regardless of whatever `workflow_status` it already had. No data-migration backfill was performed (a defensible, honest choice given the two vocabularies don't map cleanly — e.g. `ADVANCE_TO_PHONE` names a Stage while `HOLD` names an Outcome-like decision — fabricating a backfill risked inventing history that never actually happened).
- `performed_by`/`created_by`/`author` fields throughout (Stage transitions, Outcome decisions, Candidate Flags) are optional free-text strings, not linked to a real authentication/user system — none exists in Selection today (task §15 explicitly keeps RBAC out of scope), so these fields are honest placeholders ready for a future auth integration rather than a fabricated identity.
- `target_queue_label` and `future_contact_policy` are recorded and displayed but are informational metadata only — no actual queue-routing or contact-blocking mechanism exists in Selection to enforce them (none was asked for; task §11 frames the action set as intentionally small).
- `SelectionReminder` has no notification/scheduling engine behind it (task's own "no separate Event Engine" spirit applied here) — it is a visible, markable-resolved record on the Decision Summary page only.
- The Decision Summary's evidence breakdown (strongest/weaker/conflicting/unresolved) reads only the MOST RECENT Fit Assessment for the candidate; a candidate with multiple historical Fit Assessments only sees the latest one summarized there (consistent with how Primary Screening's own summary already works).

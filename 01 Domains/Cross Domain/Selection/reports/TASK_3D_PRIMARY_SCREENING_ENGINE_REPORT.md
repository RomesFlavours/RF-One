# TASK 3D — Primary Screening Engine + Hard Gates + Internal Priority Index: Implementation Report

## 1. What I implemented

A restaurant-configurable Primary Screening Engine that sits before Phone Interview: a `PrimaryScreeningCriterion` library on a fixed, universal 0–4 level scale whose *meaning* per level, coefficient, direction (positive/negative), and Hard Disqualifier behavior are entirely restaurant-authored; a `PrimaryScreeningRun` per Application holding a snapshot-frozen set of `PrimaryScreeningCriterionEvaluation` rows and an INTERNAL-only `priority_index` (a simple, transparent sum of signed `coefficient × level` contributions — never shown to the Selezionatore); a categorical Hard Disqualifier gate that removes an Application from the normal queue regardless of how positive its mathematical index is, with a mandatory-reason override that returns it to normal; explicit uncertainty states so an unevaluated Criterion is never silently coerced to level 0; system-vs-effective evaluation tracking identical to the pattern already used for Fit Assessment/Signals; immutable per-Criterion snapshots so a later restaurant edit never rewrites a historical screening run; a plain-language, non-numeric explanation engine; and a Normal Pool / Hard Disqualifier Pool queue UI. No scoring/ranking language, automatic ADVANCE_TO_PHONE, or hiring decision was introduced.

## 3. Screening Criterion model

`PrimaryScreeningCriterion` mirrors `Requirement`/`SignalDefinition`'s restaurant-owned, versioned shape, holding every field the task lists: name/description/category (free text)/target role/location context, `coefficient` (float) and `direction` (`POSITIVE`/`NEGATIVE`) kept as two separate fields (task §3/§4 — magnitude never conflated with sign), `is_hard_disqualifier`/`hard_disqualifier_trigger_level`, `evidence_sources_allowed`, four evidence-guidance fields, `display_order`, `is_active`/`version`. Nothing is seeded universally — `create_criterion()` accepts arbitrary restaurant data with no fixed list anywhere in the engine (task §10/§27).

## 4. Level 0–4 model

`core/primary_screening_model.LEVEL_SCALE = (0, 1, 2, 3, 4)` is the one universal structural constant; `PrimaryScreeningCriterion.level_descriptions` is a JSON object (`{"0": "...", ..., "4": "..."}`) holding the restaurant's own meaning for each level on that specific Criterion — the engine never interprets these strings, it only displays them next to the level a Selezionatore is choosing. `validate_level()` enforces the scale itself; it never validates or infers meaning.

## 5. Coefficient / contribution / internal Priority Index behavior

`compute_contribution(coefficient, level, direction)` implements exactly `coefficient × level`, negated when `direction == NEGATIVE` — a single, transparent multiplication, no statistical modeling. `compute_priority_index()` sums every `EVALUATED` evaluation's contribution (cumulative — never "just the strongest Criterion," verified directly). The resulting `PrimaryScreeningRun.priority_index` is persisted for internal ordering/auditability but is **never returned by any route/template for direct display** — confirmed by grepping every new template for `priority_index`/`.contribution` (zero matches) and by the live Flask smoke test below.

## 6. Hard Disqualifier behavior

A Criterion optionally declares `is_hard_disqualifier` + `hard_disqualifier_trigger_level`. `_recompute_run()` marks `evaluation.is_active_hard_disqualifier = True` when `effective_level >= trigger_level` (exactly at the configured level, never below), independent of any contribution math. `PrimaryScreeningRun.has_active_hard_disqualifier` is a categorical gate — set from whether ANY un-overridden hard-disqualifying evaluation exists, never from comparing the Priority Index against a threshold, so it cannot be mathematically cancelled by positive contributions (verified directly with a fixture where the naive sum is positive yet the Application stays disqualified). Hard-disqualified Applications are excluded from `list_normal_pool()` and surfaced separately by `list_hard_disqualifier_pool()` — never deleted.

## 7. Snapshot/version behavior

`get_or_create_criterion_snapshot()` mirrors `requirements_service.create_requirement_set_snapshot()`'s idempotent-per-version rule exactly, at single-Criterion granularity (`PrimaryScreeningCriterionSnapshot`, unique on `(criterion_id, version)`). `create_screening_run()` always snapshots the criterion's CURRENT version at creation time and every `PrimaryScreeningCriterionEvaluation` links to that frozen snapshot, never to the live Criterion row — verified directly: editing a live Criterion's coefficient/direction after a run exists leaves that run's own snapshot (and its already-computed contribution) completely unchanged, while a brand-new run created afterward correctly picks up the new configuration in its own fresh snapshot.

## 8. Screening evaluation/evidence model

`PrimaryScreeningCriterionEvaluation` is the Primary Screening counterpart of `RequirementAssessment`: `status` (`EVALUATED`/`INSUFFICIENT_EVIDENCE`/`NOT_APPLICABLE`/`NOT_EVALUATED` — an Application starts every Criterion at `NOT_EVALUATED`, never silently level 0, verified directly), `system_level` (only ever set by the optional automatic Signal-mapping path) vs. `effective_level` (what the Priority Index actually uses), `confidence`/`evidence_source`/`evidence_text`/`explanation` for traceability, `origin` (`SYSTEM_GENERATED`/`HUMAN_ENTERED`/`HUMAN_CONFIRMED`/`HUMAN_OVERRIDDEN`), and separate Hard-Disqualifier-override fields. `human_enter_evaluation()`/`human_confirm_evaluation()`/`human_override_evaluation()` follow the identical system/effective pattern already used everywhere else in Selection: overriding preserves `system_level` untouched and only changes `effective_level`, `origin`, and records the reason/timestamp.

## 9. Primary Screening Queue

`list_normal_pool(restaurant_id, limit=None)` returns the most recent run per Application (excluding hard-disqualified ones), sorted by the internal index descending; `limit` is a pure display convenience ("first 10/20/50/all" on the Queue page) that never changes any underlying decision (task §21). The Queue page shows candidate/role/date, the plain-language explanation, an unresolved-evidence badge, a repeated-applicant badge, Open Original CV ↗, and links to the full Application and the per-Criterion screening detail — never a numeric rank position. `run_screening_for_unscreened_applications()` gives a practical bulk action for the task's own "200 Applications" scenario without ever re-screening (and so never silently changing) an Application that already has a run.

## 10. Hard Disqualifier pool

`list_hard_disqualifier_pool()` returns the same kind of run objects, filtered to `has_active_hard_disqualifier == True`, sorted the same way. The dedicated Queue section shows exactly this pool with the specific triggering Criterion name(s), the explanation, Original CV ↗, and a "Review / Override" link — Applications here remain fully queryable/reviewable and are never deleted (verified directly: `app_svc.get_application()` still returns the row after disqualification).

## 11. Selezionatore override behavior

`override_hard_disqualifier(evaluation_id, reason)` raises `ValueError` on a blank/whitespace-only reason (verified directly, and reproduced live over HTTP — an empty-reason POST left `hard_disqualifier_overridden` at `False`). A valid reason sets `hard_disqualifier_overridden=True` plus the reason/timestamp while leaving `is_active_hard_disqualifier`, the original level, and all evidence completely visible (task §8's "do not erase historical evidence") — `_recompute_run()` then excludes this evaluation from `has_active_hard_disqualifier`, which is what actually returns the Application to the normal pool (verified directly, and reproduced live: the Queue's Normal/Hard Disqualifier pool counts flipped from 0/1 to 1/0 after the override). Nothing here touches `Application.workflow_status` — advancing to Phone Interview afterward remains the Selezionatore's own separate, existing action.

## 12. UI/configuration added

`/primary-screening-criteria` (+ `/new`, `/<id>/update`, `/<id>/toggle-active`) for restaurant configuration — name/description/category/role/location, coefficient, direction, Hard Disqualifier + trigger level, all five level meanings, allowed evidence sources, four evidence-guidance fields, and the optional Signal auto-evaluation mapping. `/primary-screening-queue` (+ `/run-all`), `/applications/<id>/primary-screening/run`, `/primary-screening/<run_id>` (detail — evaluations, level entry/override/confirm, Not Applicable/Insufficient Evidence, Hard Disqualifier override, Original CV ↗), plus the underlying `/evaluations/<id>/...` action routes.

## 14. Known limitations directly relevant to Task 3D

- Automatic (`SYSTEM_GENERATED`) Criterion evaluation only exists for the one deterministic path the task's own architecture allows: an optional restaurant-configured Signal-status → level mapping (mirroring `ReviewPriorityPolicyRule`'s exact pattern). RF-One has no way to auto-score an arbitrary restaurant-defined Criterion from free-text résumé/Application content without restaurant-specific judgment the engine does not (and per task §1 must not) possess — every other Criterion is Selezionatore-entered. This is a deliberate scope boundary, not an oversight; a restaurant with no Signal-linked Criteria will see every Application land at `priority_index = 0.0` until the Selezionatore starts entering levels.
- `location_label` exists on the Criterion (task §1's own field list) but is not currently used as a filter when selecting which Criteria apply to a given Application/run — only `target_role` is — since this single-restaurant MVP has no multi-location Application concept yet to filter against, matching the same documented limitation already noted for Phone/In-Person Interview Sections.
- A `PrimaryScreeningRun`'s explanation names at most the top 2 positive and top 2 negative factors and up to 3 uncertain ones; it does not attempt to summarize every evaluated Criterion.

# TASK 4B — In-Person Interview + Practical Assessment + Consistency Engine: Implementation Report

## 1. What I implemented

A persistent In-Person Interview + Practical Assessment framework, built entirely on Task 3B Fit Assessment / Task 3C Selection Signal evidence and Task 4A Phone Interview carry-forward, plus a new deep Consistency Engine: a restaurant-configurable `InPersonInterviewPlan` pinned to the same immutable Requirement Set snapshot and Fit Assessment already in use (and linked to the Phone Interview Plan where one exists); restaurant-configurable interview Sections and Assessment Items (Question/Observation/Practical Test/Role-Play/Consistency Check/Carry-Forward/Courtesy) in one unified, copy-by-value instance model; automatic carry-forward of unresolved Phone Interview items; direct in-person observations and hands-on Practical Assessment, both bridging into the *existing* Fit Assessment/Signal evidence models (never a parallel system); a Consistency Thread/Statement model comparing CV, prior Applications, Phone Interview and In-Person Interview evidence on one topic at a time, with six neutral comparison statuses and clarification-question generation — never an automatic dishonesty conclusion; variable-length interviews the Selezionatore can stop at any point without losing anything; and Original CV access throughout. No ranking, scoring, or hiring decision was introduced.

## 3. In-Person persistence model

`InPersonInterviewPlan`: one row per Application (unique FK), storing `requirement_set_snapshot_id`/`fit_assessment_id` (authoritative, never repointed), `phone_interview_plan_id` (nullable — linked automatically where a Phone Interview Plan exists), `status` (the interview PROCESS status — `NOT_STARTED`/`IN_PROGRESS`/`COMPLETED`/`STOPPED_EARLY`, kept separate from `Application.workflow_status`, and with no Escape Route concept — Task 4B does not ask for one), and `notes`. `AssessmentItemInstance` is ONE unified table serving every item type — a Question's answer, an Observation's note, and a Practical Test's performance record are all the same "RAW INPUT" concept (task's own §16 grouping), stored in one `raw_response` field plus a separate `selezionatore_note` interpretation field, `confidence`, and `status` (`NOT_DONE`/`DONE`/`PARTIAL`/`UNRESOLVED`/`SKIPPED`). Every instance copies its text/objective/importance by value at entry time, exactly like `PhoneInterviewQuestionInstance` — a later edit to a live Definition never rewrites history.

## 4. Interview Section / Assessment Item model

`InPersonInterviewSectionDefinition` (restaurant/role-scoped, reorderable, active/version) carries an optional `section_kind` tag (`CARRY_FORWARD`/`WELCOME_OBSERVATION`/`WORK_PERSONALITY`/`HOSPITALITY_MOTIVATION`/`PRACTICAL_TECHNICAL`/`COMMITMENT`/`FINAL_OBSERVATION`/`OTHER`) used only to recognize the Final Observation phase — nothing in the framework hard-codes one universal sequence; Rome's Flavours' 6-section structure (Carry-Forward is generated directly onto items, not a configured Section) is seeded as ordinary restaurant data. `AssessmentItemDefinition` belongs to one Section and supports every field the task lists: type, title/instruction/scenario/objective, linked Requirement(s)/Signal(s), importance, mandatory-within-process, four evidence-guidance fields, Selezionatore instructions, display order, active/inactive, version.

## 5. Carry-forward behavior

`_add_carry_forward_items()` pulls every Phone Interview Question Instance left `NOT_ASKED`/`PARTIALLY_ANSWERED`/`UNRESOLVED`/`CARRIED_FORWARD` (Courtesy questions excluded) and copies the original question text, original answer (if any), its Requirement/Signal link, its importance, and why it remains unresolved into a new `CARRY_FORWARD`-type `AssessmentItemInstance` — the source Phone Interview row itself is never touched. These items are placed in their own always-first section (`section_display_order=-1`, satisfying "should appear early according to importance").

## 6. Practical Assessment behavior

A `PRACTICAL_TEST` item is the same `AssessmentItemInstance` shape as every other type: `scenario`/`instruction` hold the setup and instructions to the candidate, `selezionatore_instructions` holds what to observe, `raw_response` holds the response/performance notes, and `confidence` holds the Selezionatore's own confidence marker — no numeric score anywhere. Rome's Flavours' example SERVER practical content (dish description, pasta-recommendation role-play, appetizer/entrée timing, no-active-tables scenario, side work/opening/closing duties, full service sequence, "train me" role-play, wine knowledge/presentation/equipment handling) is seeded as restaurant data in `seed_romes_flavours_in_person_interview_structure()`.

## 7. Consistency Engine model

A `ConsistencyThread` (topic, importance, `comparison_status`, `explanation`, `confidence`, `selezionatore_resolution`) is scoped to the Application (spans the whole selection process, not one interview) and holds append-only `ConsistencyStatement` rows (source stage, source reference, source date, raw statement, optional normalized interpretation) — an original statement is never edited or deleted, even after the thread's status changes. Six statuses are supported: `CONSISTENT`, `MINOR_VARIATION`, `MATERIAL_INCONSISTENCY`, `UNRESOLVED` (the default, e.g. when only one statement exists), `EXPLAINED_DIFFERENCE`, and `NEW_INFORMATION` (added beyond the task's own minimum five, needed for §14's own "distinguish new information from material contradiction"). `set_comparison_status()` is the only place a status is ever set — a deliberate, explicit call, never inferred from free-text content by this codebase (the same no-NLP-judgment rule every prior Selection task follows); the explanation text is always a plain factual description, never a psychological or legal conclusion.

## 8. Cross-source comparison behavior

`add_statement_from_phone_answer()`/`add_statement_from_in_person_item()`/`add_statement_from_application()` pull already-captured raw text (never re-typed) from a Phone Interview answer, an In-Person response, or a CV/Application/prior-Application record respectively, so one thread can compare any combination — CV vs. Phone, Phone vs. In-Person, or all three at once. `generate_cross_application_consistency_threads()` reuses Task 3C-FIX's own facts-only `application_comparison.compare_applications()` (structured, normalized profile facts only) to auto-create one thread per concrete change against the most recent prior Application, always classified `NEW_INFORMATION` first — a change is never automatically negative; the Selezionatore may reclassify it to `MATERIAL_INCONSISTENCY` later if warranted.

## 9. Clarification-question behavior

`generate_clarification_item()` turns an open Consistency Thread into a `CONSISTENCY_CHECK` Assessment Item in the plan, quoting every existing statement's raw text verbatim (never inventing what was said) in a plain, neutral template matching the task's own example shape. `list_items_to_verify()` surfaces only `MATERIAL_INCONSISTENCY`/`UNRESOLVED` threads, sorted by importance — never the full thread list. `add_follow_up_item()` (Assessment Item follow-ups, separate from Consistency clarification) preserves why it was generated via `reason_for_inclusion`.

## 10. Fit Assessment / Signal integration

`record_response_as_fit_evidence()`/`record_response_as_signal_evidence()` call `fit_assessment_service.add_evidence()`/`signal_service.add_evidence()` directly — no parallel evidence system. The evidence `source_type` is chosen automatically from the item: `PRACTICAL_ASSESSMENT_RESULT` for a Practical Test, `IN_PERSON_OBSERVATION` for everything else (both already existed in `core/fit_assessment_model.py` from Task 3B). All prior résumé/Phone evidence is preserved (append-only); adding Signal evidence recomputes Review Priority through the existing mechanism.

## 13. Known limitations directly relevant to Task 4B

- **One real bug was found and fixed during testing**: the synthetic-fixture cleanup in `_assert_selection_4b_in_person_interview` initially deleted `ConsistencyThread` rows before the `AssessmentItemInstance` rows that reference them via `consistency_thread_id`, causing a `FOREIGN KEY constraint failed` (SQLite foreign-key enforcement is on for this engine). Fixed by reordering the cleanup to delete item instances first. This was a test-fixture ordering bug, not a defect in `in_person_interview_service.py` itself.
- Consistency comparison status is never auto-classified from free-text content (the same no-NLP-judgment rule every prior Selection task follows) — a thread's status is always an explicit call, either by the Selezionatore or by the narrow, deterministic `generate_cross_application_consistency_threads()` classifier for structured facts only. RF-One does not attempt to read two free-text answers and decide on its own whether they conflict.
- `refresh_plan()`'s "safe to fully regenerate" branch only applies while `plan.status == NOT_STARTED`, mirroring Task 4A's own Phone Interview Plan behavior.
- The clarification-question template is a single generic phrasing (quoting every statement verbatim); it does not vary its wording by topic or source-stage combination.

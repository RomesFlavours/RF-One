# AI-generated Recognition Profiles under human approval

Bank unification, Phase 2 (Product Owner, 2026-10-24). Permanent feature: the AI builds and maintains the
Recognition Profiles of the one engine; a person approves every profile before it acts. No new rule system:
the existing profile conversation, research, Preview, Save, versions and rollback are the cycle.

## 1. The cycle

| Step | Where | State |
|---|---|---|
| WHO recognised without a profile | C-Bank run: exception `NO_PROFILE`, grouped by WHO on the Guided Reconciliation dashboard | implemented |
| Analysis of Labels and history | Profile conversation context: history, research, catalog, previous version, and (Phase 2) `who_context` = the WHO's Labels with definitions, its APPROVED WHYs and its historical WHYs (evidence only) — `bank_flow_routes.who_context` | implemented |
| AI proposal | "Propose profile with AI" on a `NO_PROFILE` group opens `/bank/ai-rules?who_id=…&propose=1`: the existing PHOTO conversation of that WHO, with a first request to the AI | implemented |
| Conditions by type / Source / LLC / WHY-WHAT | Existing profile branches: conditions on description, memo, who, source, source_class, owner, direction, category, amount, date | existing |
| Preview | Existing Preview over the current record or the whole repository (`flow.plan`), before any save | existing |
| Approve / modify / reject | Approve = Save after Preview; modify = continue the conversation; reject = Discard | existing |
| Activation only after approval | Save publishes an immutable version; nothing is active before | existing |
| One profile per WHO | `bind_profile` reuses the WHO's profile and refuses a second managed one | existing (legacy text rules can still duplicate a WHO: see the Phase 2 report) |
| Versions and rollback | Immutable versions, history, guarded rollback of applications | existing |

Labels are context only: they never become a classification and never prevail over a profile or an approved
WHO → WHY association. Human decisions are never changed by a profile proposal.

## 2. What is a proposal today

An AI proposal lives in its profile conversation (`BankFlowArtifact`, kind CHAT) with its draft definition
until a person saves it: it is not a rule, it is never applied, and it can be reopened, changed or
discarded. This needs no schema change.

## 3. PROPOSED as a rule state (specification only — not migrated)

Needed only if proposals must be listed and approved outside their conversation (e.g. a queue of AI
proposals generated by a run).

1. `bank_ai_rules.status` gains `PROPOSED` (`ck_bank_ai_rule_status` → `ACTIVE`, `INACTIVE`, `PROPOSED`):
   one Alembic migration on SQLite (batch alter of the check constraint), no data change.
2. `flow.entries` already reads only `ACTIVE` rules: a `PROPOSED` profile can never classify.
3. The AI writes a proposal as a new rule (or a new version of the WHO's profile) with status `PROPOSED`
   and `apply_future = false`; its Preview is the existing one.
4. Approve = the existing Save: status `ACTIVE`, `apply_future` as chosen, application audit and rollback
   as today. Reject = `INACTIVE` with the reason in the version text; nothing is deleted.
5. One proposal per WHO at a time; a new proposal for the same WHO replaces the pending one (new version).
6. A proposal never touches transactions until it is approved and applied.

Migration, deploy and AWS are out of scope until the Product Owner approves them.

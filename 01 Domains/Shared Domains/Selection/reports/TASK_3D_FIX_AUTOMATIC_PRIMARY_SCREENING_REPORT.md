# TASK 3D-FIX — Automatic Primary Screening Evaluation from Application Evidence: Implementation Report

## 1. What I implemented

A generic, AI-assisted automatic evaluator for Primary Screening Criteria that have no deterministic Signal mapping — the operational gap Task 3D itself documented. Any restaurant-authored Criterion (its own name, description, 0-4 level meanings, guidance, and allowed evidence sources) is now interpreted against a structured evidence package built entirely from evidence already persisted in Selection (résumé facts, Application/Application-history, Fit Assessment, Selection Signals, Selezionatore notes). The engine never contains criterion-specific logic; it never fabricates a level; every failure (no AI provider configured, a request failure, or malformed output) leaves the Criterion explicitly unresolved rather than guessed. The existing deterministic Signal-mapping shortcut is preserved and preferred. Batch screening (`run_screening_for_unscreened_applications`) and re-evaluation (re-running `create_screening_run`) both now exercise this evaluator automatically, so a large applicant pool no longer needs every Application opened manually. Selezionatore notes are now supported on both the overall Screening Run and each individual Criterion Evaluation, reusing the existing `ApplicationNote` mechanism rather than a new one.

## 2. Main files changed

New: `rfone_data_store/selection/primary_screening_ai_evaluator.py` (evidence-package builder, prompt builder, structured-output validator, `evaluate_criterion_with_ai`), migration `b3d7f2a9c5e1_add_selection_3d_fix_automatic_screening.py` (+2 columns).
Extended: `models.py` (`PrimaryScreeningCriterionEvaluation.evidence_items` JSON list; `ApplicationNote.context_type`/`.context_id` for source-tagged notes), `primary_screening_service.py` (`_auto_evaluate_generic` fallback wired into `create_screening_run`/`run_screening_for_unscreened_applications`; `add_run_note`/`list_run_notes`/`add_evaluation_note`/`list_evaluation_notes`), `application_service.py` (`add_note`/`list_notes` gained optional `context_type`/`context_id`), `03 Software/Selection/app.py` (`primary_screening_run_add_note`, `primary_screening_evaluation_add_note` routes; `primary_screening_detail` now passes notes), `rfone_data_store/selection_validation.py` (+27 new checks in `_assert_selection_3d_fix`), `03 Software/Selection/test_batch_upload.py` (+5 Flask-layer checks).

## 3. Generic automatic evaluator architecture

`primary_screening_ai_evaluator.evaluate_criterion_with_ai(session, application, criterion_snapshot, *, generate_json_fn=None)` is the entire contract — it takes a Criterion **snapshot** (never the live, editable row) and returns a validated `AIEvaluationResult`, or raises `AIEvaluationUnavailable`. It contains zero `if criterion.name == ...` branches; it interprets whatever `level_descriptions`/`evaluation_guidance`/`evidence_*_guidance`/`evidence_sources_allowed` the snapshot carries. `create_screening_run` calls the deterministic Signal-mapping shortcut first (unchanged, Task 3D); only when that doesn't reach `EVALUATED` does it call the generic evaluator (`_auto_evaluate_generic`) — verified directly (3D-FIX-M: a fake AI function raises if ever consulted for a Criterion the deterministic path already resolved, and that assertion never fires).

## 4. Evidence-package construction

`build_evidence_package()` gathers, from data already persisted in Selection: résumé facts (work history with dates/role family, education, skills, certifications, languages, summary, declared availability, location — via `persistence.to_profile`), Application context, Application history + the existing change-since-prior-application summary (Task 3C-FIX), Fit Assessment evidence (`EVIDENCED`/`PARTIALLY_EVIDENCED`/`CONFLICTING_EVIDENCE` requirements only), existing Selection Signal observations, and existing Selezionatore notes — grouped by the same `EVIDENCE_SOURCES` vocabulary Task 3D already defined. It deliberately never reads Phone/In-Person/Consistency data (task's own "must NOT depend on Phone or In-Person evidence for the initial run"). Nothing is duplicated — every item carries a `source_reference` back to where it already lives (e.g. `work_history: Riverside Grill`, `signal: 3D-FIX Recency Signal`).

## 5. Structured AI output contract

`build_prompt()` embeds the Criterion's own level 0-4 meanings, guidance, and the evidence package, and explicitly instructs FACT vs. DERIVED INFORMATION vs. INFERENCE, conservative choice under weak/ambiguous evidence, and never defaulting to level 0. `_validate_and_parse()` enforces the exact contract from the task spec: `status` must be one of `EVALUATED`/`INSUFFICIENT_EVIDENCE`/`NOT_APPLICABLE`; `level` must be a whole number 0-4 only when `status == EVALUATED` (forced to `None` otherwise); `confidence` normalizes to `UNKNOWN` if outside `HIGH/MEDIUM/LOW/UNKNOWN`; `explanation` must be non-empty; `evidence` must be a list, with each item's `source_type` coerced to `OTHER` if unrecognized. Anything else (wrong types, out-of-range level, non-list evidence) raises immediately — never silently repaired into a candidate evaluation. An `EVALUATED` response with zero cited evidence items is downgraded to `INSUFFICIENT_EVIDENCE` (every material conclusion must be evidence-grounded).

## 6. Failure/fallback behavior

Any failure — no `ANTHROPIC_API_KEY` configured (the actual state of this environment), a request exception, or a validation failure — is caught and re-raised as the single sentinel `AIEvaluationUnavailable`, mirroring `parsing/resolve.py`'s existing `ProviderUnavailable` fallback convention exactly. `_auto_evaluate_generic()` catches this and leaves the Criterion Evaluation exactly as the deterministic step left it (`NOT_EVALUATED`, with the failure reason recorded in `explanation` only when nothing more informative was already there); it never raises, so one Criterion's failure never stops the rest of the run or the batch. Verified directly against the REAL (no-fake-function) unavailable path, not just a simulated one.

## 7. System/effective evaluation behavior

Reuses Task 3D's architecture unchanged: a successful automatic evaluation sets `system_level`/`effective_level` (initially equal) and `origin = SYSTEM_GENERATED`. `human_override_evaluation`/`human_confirm_evaluation` are untouched — an override changes `effective_level` and `origin` but never touches `system_level` or `evidence_items`, verified directly (3D-FIX-T).

## 8. Hard Disqualifier interaction

No new logic was needed: `_recompute_run()` already reads `evaluation.status`/`effective_level` uniformly regardless of which evaluator populated them, so a generically (AI-assisted) evaluated Criterion that meets its configured trigger level automatically activates the same categorical, never-mathematically-cancelled Hard Disqualifier gate Task 3D already built — verified directly, including that the existing `override_hard_disqualifier()` mandatory-reason mechanism still works against an automatically detected one.

## 9. Batch Screening behavior

`run_screening_for_unscreened_applications()` is unchanged in shape (screens every run-less Application in the restaurant) but now transitively exercises the generic evaluator through `create_screening_run()` for every applicable Criterion on every Application — so a 200-Application batch no longer leaves non-Signal-linked Criteria stuck at `NOT_EVALUATED`. An optional `ai_generate_json_fn` parameter threads through both functions purely as a test/DI seam; production callers never pass it.

## 10. Re-evaluation behavior

Unchanged from Task 3D by design: `create_screening_run()` always creates a brand-new `PrimaryScreeningRun` with fresh Criterion snapshots at the CURRENT live-Criterion version — this already *is* the explicit re-evaluation action the task asked for. Verified directly that editing a live Criterion's level descriptions never alters an already-created evaluation's historical snapshot (3D-FIX-AA), and that re-running produces a new run against the new configuration while the old run's own result/explanation stay exactly as they were (3D-FIX-AB).

## 11. Notes support

`ApplicationNote` (Task 3C-FIX) gained two nullable, indexed columns — `context_type`/`context_id` — rather than a new notes table. `primary_screening_service.add_run_note`/`add_evaluation_note` tag notes `"PRIMARY_SCREENING_RUN"`/`"PRIMARY_SCREENING_CRITERION_EVALUATION"` with the relevant id; `list_run_notes`/`list_evaluation_notes` filter to that context, while the existing unfiltered `application_service.list_notes()` still returns every note for an Application regardless of context — exactly the "queryable by Application and by source/context" shape the task asked for, ready for a future Final Selection Decision screen to aggregate. Verified directly that adding notes never changes the Priority Index.

## 12. UI changes

`primary_screening_detail.html`: each Criterion Evaluation now shows its `confidence` and, when present, the structured `evidence_items` list (source type, reference, evidence text, interpretation) instead of only the single legacy `evidence_text` line; a new "Notes on this Screening Run" section and a per-evaluation "Notes on this Criterion Evaluation" `<details>` section, each with its own add-note form and timestamped history. No other page needed changes: the Primary Screening Queue and detail pages already never rendered the numeric Priority Index (Task 3D's own design), and the Original CV action was already present — both re-verified, not modified.

## 14. Known limitations directly relevant to this fix

- No `ANTHROPIC_API_KEY` is configured in this environment (confirmed unchanged from Task 3D/4A/4B), so the AI-assisted path itself has never been exercised against a real provider here — only its full contract (evidence package, prompt, structured-output validation, failure handling) has real-world mileage, via the injectable `generate_json_fn` seam used in tests. The real-unavailable path (no seam, no key) is separately and directly verified to never crash.
- The evaluator makes one AI call per (Application, unresolved Criterion) pair with no batching/caching across a run — for a genuinely large batch (200 Applications × several Criteria) with a real provider configured, this is many sequential calls; nothing here parallelizes or batches them, since doing so was not asked for and would add complexity beyond this fix's scope.
- `evidence_sources_allowed` on a Criterion is passed to the AI prompt as guidance only, not enforced as a hard filter on which evidence is gathered — consistent with how the same field is already treated elsewhere in Selection (e.g. `signal_service.add_evidence` never filters by it either), but worth knowing if a future task wants it to be a strict allow-list.
- The Fit Assessment evidence gathered is a concise one-line-per-Requirement summary (status + first evidence snippet), not the full evidence history — sufficient for the evaluator's own conservative use, but not a complete replay of everything recorded in a Fit Assessment.

# TASK 4A — Phone Interview Framework + Core Question Library: Implementation Report

## 1. What I implemented

A universal Phone Interview framework that begins when an Application reaches `ADVANCE_TO_PHONE`: a persistent `PhoneInterviewPlan` pinned to the same immutable `RequirementSetSnapshot`/`FitAssessment` already used at résumé stage; a restaurant-configurable Core Question library (`PhoneInterviewQuestionDefinition`, also used for Escape Route Courtesy Questions); a Dynamic Question generator that reads existing Fit Assessment gaps (`NOT_ASSESSED_AT_THIS_STAGE` now assessable at phone, `PARTIALLY_EVIDENCED`, `CONFLICTING_EVIDENCE`), Selection Signals left `POSSIBLE`/`CONFLICTING`, and repeated-application changes; Sine Qua Non/Gate Questions with a separate Gate Evaluation (`PASSED`/`FAILED`/`UNCLEAR`/`NOT_ASKED`) that never auto-rejects; an explicit Selezionatore-activated Escape Route (unresolved substantive questions preserved, 2–3 courtesy questions offered); variable-length interview support (Selezionatore stops at any point, nothing is ever deleted); follow-up questions; answer capture that bridges into the *existing* Fit Assessment/Signal evidence models (never a parallel evidence system); automatic carry-forward of unresolved/partially-answered/not-asked questions to a future In-Person Interview; and a Selezionatore-only post-interview decision (`ADVANCE_TO_IN_PERSON`/`HOLD`/`STOP`) that reuses `Application.workflow_status`. No ranking, scoring, or automatic hiring decision was introduced anywhere.

## 3. Phone Interview persistence model

`PhoneInterviewPlan`: one row per Application (unique FK), storing `person_id`/`candidate_id`/`restaurant_id` (denormalized, like `FitAssessment.requirement_set_id`), `requirement_set_snapshot_id` + `fit_assessment_id` (authoritative — never repointed to a newer live Requirement Set), `status` (the interview PROCESS status — `NOT_STARTED`/`IN_PROGRESS`/`ESCAPE_ROUTE`/`COMPLETED`/`STOPPED_EARLY`, deliberately distinct from `Application.workflow_status`), `notes`, and `escape_route_activated_at`/`escape_route_reason`. `PhoneInterviewQuestionInstance`: one row per question actually placed into a plan, copy-by-value of its text/objective/importance at entry time (so a later edit to a live Definition never rewrites history — the `RequirementSnapshotItem` discipline), with `source_type` (CORE/DYNAMIC/COURTESY/FOLLOW_UP), `linked_requirement_ids` (pointing at the plan's own pinned `RequirementSnapshotItem` rows, resolved from a Definition's live-Requirement links via `_resolve_snapshot_requirement_ids`), `linked_signal_definition_ids`, `importance`, `is_sine_qua_non`, `mandatory_within_selection_process`, `status`, `gate_evaluation`, `answer_text`/`selezionatore_note` (kept separate), `carried_forward_reason`, and self-referential `parent_question_instance_id` for follow-ups.

## 4. Core Question Library model/UI

`PhoneInterviewQuestionDefinition` mirrors `Requirement`/`SignalDefinition`'s shape exactly: restaurant/role scoping, `importance`, `is_sine_qua_non`, `mandatory_within_selection_process`, `assessment_stages`, `follow_up_guidance`, `is_courtesy` (marks a Definition as an Escape Route closing question rather than an ordinary Core Question — same table, since both are structurally identical restaurant data), `display_order`, `is_active`/`version`. Full CRUD UI at `/phone-interview-questions` (list, create, edit, activate/deactivate) — mirrors `signals_home.html`'s pattern. `industry/restaurant_templates.py`'s new `seed_romes_flavours_phone_interview_questions()` seeds Rome's Flavours' own example SERVER content (§18's Sine Qua Non/Reliability/Attitude/Motivation/Hospitality questions plus 2 Courtesy questions) as ordinary restaurant data — the universal engine (`core/phone_interview_model.py`/`phone_interview_service.py`) has no knowledge this seed function exists. None of the seeded or example content touches a protected characteristic (§19); reliability/attendance topics are asked directly.

## 5. Dynamic Question generation behavior

`phone_interview_service.generate_plan_questions()` runs three deterministic (never LLM/inference-based) sub-generators, each only ever *adding* instances not already present: (1) `_add_dynamic_requirement_questions` — one question per `RequirementAssessment` assessable at `PHONE_INTERVIEW` whose effective status is `NOT_ASSESSED_AT_THIS_STAGE`/`PARTIALLY_EVIDENCED`/`CONFLICTING_EVIDENCE`, importance mapped from the Requirement's own criticality (`MUST_HAVE`/`DISQUALIFIER`→`CRITICAL`, `PREFERRED`→`HIGH`, `OPTIONAL`→`MEDIUM`); (2) `_add_dynamic_signal_questions` — one question per Signal Observation left `POSSIBLE`/`CONFLICTING` in the `READINESS_RECENCY`/`MOTIVATION_PERSONAL`/`MOTIVATION_PROFESSIONAL` families, quoting the Signal's own recorded rationale rather than inventing one; (3) `_add_dynamic_repeat_application_question` — one question when Task 3C-FIX's facts-only `compare_applications()` shows a material change. Every generated question retains a concrete `reason_for_inclusion` and its source Requirement/Signal link.

## 6. Gate / Sine Qua Non behavior

The restaurant configures which Core Questions are Sine Qua Non (`is_sine_qua_non=True`) — the framework itself never assumes one. `question_sort_key()` places every Gate Question in a bucket that sorts before all others regardless of its own importance level. `set_gate_evaluation()` records `PASSED`/`FAILED`/`UNCLEAR`/`NOT_ASKED` separately from the raw answer, and only applies to Sine Qua Non instances (raises otherwise). A `FAILED` Gate never touches `Application.workflow_status` or anything else automatically — verified directly (targeted test J).

## 7. Escape Route behavior

`activate_escape_route()` is an explicit, Selezionatore-only call: it sets `plan.status = ESCAPE_ROUTE`, flips every still-`NOT_ASKED` substantive (CORE/DYNAMIC/FOLLOW_UP) instance to `UNRESOLVED` (never deleted), and generates 2–3 Courtesy Question instances from the restaurant's own configured `is_courtesy=True` Definitions (role-matched, capped at 3) — falling back to two generic, protected-characteristic-free closing lines only when the restaurant has configured none yet. `get_ordered_remaining_questions()` excludes Courtesy questions from the ordinary priority queue; they are surfaced in their own dedicated UI section, shown only while `plan.status == ESCAPE_ROUTE`.

## 8. Question ordering / variable-duration behavior

`question_sort_key(is_sine_qua_non, importance, display_order)` returns `(gate_bucket, importance_bucket, display_order)`; `get_ordered_remaining_questions()` sorts only the still-`NOT_ASKED` questions by this key (GATE → CRITICAL → HIGH → MEDIUM → LOW), while `list_question_instances()` (unfiltered, `display_order` ascending) gives the interview's own stable history — so an already-asked question's row is never reordered or touched once the interview has started (`refresh_plan()` only fully regenerates while `plan.status == NOT_STARTED`; afterward it only appends missing Core/new Dynamic questions among the untouched remainder). The Selezionatore may stop at any point via the post-interview decision — no fixed duration is enforced anywhere.

## 9. Answer / follow-up / evidence behavior

`record_answer()` is the one mutation point for a Question Instance's `status`/`answer_text`/`selezionatore_note` (raw text preserved verbatim, note kept in a separate field) and auto-flips the plan from `NOT_STARTED` to `IN_PROGRESS` on first use. `add_follow_up_question()` creates a `FOLLOW_UP`-sourced instance linked to its parent; nothing in the framework ever labels a candidate (e.g. "conflictual", "unreliable") — verified structurally (no such column exists on the model at all). `record_answer_as_fit_evidence()`/`record_answer_as_signal_evidence()` call `fit_assessment_service.add_evidence()`/`signal_service.add_evidence()` directly with `source_type=PHONE_INTERVIEW_RESPONSE` — no parallel evidence table was created; earlier résumé-stage evidence is untouched (append-only), and adding Signal evidence recomputes Review Priority via the existing mechanism.

## 10. Carry-forward behavior

`record_post_interview_decision()` calls `_carry_forward_unresolved()`, which marks every substantive (non-Courtesy) instance still `NOT_ASKED`/`PARTIALLY_ANSWERED`/`UNRESOLVED` as `CARRIED_FORWARD`, recording a `carried_forward_reason` that names the prior status and — when `mandatory_within_selection_process` is set — explicitly notes the restaurant's own requirement that it still be addressed before a final decision (Task 4A §17's own distinction: mandatory-during-phone vs. mandatory-before-final-decision). Nothing is deleted; Task 4A does not implement the In-Person Interview itself, only this clean hand-off.

## 11. Post-phone Selezionatore decision behavior

`record_post_interview_decision(plan_status, application_decision, reason)` is the single explicit action: it sets the Plan's own process status, runs carry-forward, and calls `application_service.set_workflow_status()` with `ADVANCE_TO_IN_PERSON`/`HOLD`/`STOP` (a new value added to the existing `WORKFLOW_STATUSES`/`DECISION_STATUSES` vocabulary, reused rather than duplicated) plus the Selezionatore's free-text reason. Nothing else in the codebase ever sets one of these three values — verified directly (targeted tests J/W/X).

## 14. Known limitations directly relevant to Task 4A

- Dynamic Question text is template-based (deterministic string construction from the Requirement/Signal's own recorded name/description/rationale), never LLM-generated — a deliberate conservative choice consistent with the rest of Selection Core's evidence matchers, not an oversight.
- `refresh_plan()`'s "safe to fully regenerate" branch only applies while `plan.status == NOT_STARTED`; there is currently no UI affordance to preview what a refresh would add before applying it.
- The follow-up mechanism lets a Selezionatore type any free-text follow-up question; RF-One does not auto-suggest follow-up wording from the answer's content (task's own `follow_up_guidance` field on a Core Question Definition is authored guidance for the human, not an automatic suggestion engine).
- Migration `1d4f7a9b2c6e` was authored by hand, following the exact structure/conventions of the prior Selection migrations, but (see above) could not be applied against a real database in this environment to confirm it runs cleanly end-to-end.

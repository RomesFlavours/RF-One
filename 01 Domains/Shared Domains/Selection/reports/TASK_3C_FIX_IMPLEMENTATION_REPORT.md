# TASK 3C-FIX — Identity Resolution + Signal Configuration + Review Queue Completion: Implementation Report

## 1. What I implemented

Four operational gaps left open by Task 3C's own documented limitations are now closed: (1) confidence-based `CandidatePerson` identity resolution (email/phone/name), with ambiguous matches surfaced for Selezionatore confirm/reject rather than auto-merged; (2) full CRUD authoring UI/service for Selection Signal Definitions; (3) full CRUD authoring UI/service for Review Priority Policies and their rules, kept structurally separate from Signal detection; (4) the Review Queue completed into an operational tool — workflow status (NEW/IN_REVIEW/ADVANCE_TO_PHONE/HOLD/STOP, Selezionatore-only), decision reasons, Selezionatore notes with history, repeated-applicant/change-since-prior visibility, system-vs-effective Review Priority display, and an "Open Original CV ↗" action from the Review Queue, Application Review, and Candidate detail screens. No ranking, scoring, or automatic status transition was introduced anywhere.

## 3. CandidatePerson identity-resolution behavior

`identity_service.resolve_or_create_person()` replaces Task 3C's email-only match: normalized email exact match, or normalized phone exact match (digits-only, common US/CA country-code prefix stripped) → **VERY_STRONG**, auto-attaches to the existing person, same as before but now covering phone too. No exact contact match → a brand-new `CandidatePerson` is created; a normalized-full-name match against another existing person is recorded as **STRONG** (exact name), or **POSSIBLE** (same surname + first-initial only) — neither ever auto-attaches. Biometric/protected-characteristic matching is out of scope and was not implemented.

## 4. Ambiguous-match / Selezionatore confirmation behavior

Every STRONG/POSSIBLE suggestion becomes a `PersonMatchCandidate` row (PENDING/CONFIRMED/REJECTED), visible both inline on the affected Application (`application_detail.html`) and in a dedicated `/identity-matches` queue. Confirming (`identity_service.confirm_match`) reassigns only `Application.person_id` to the suggested person and marks `Application.identity_origin = HUMAN_CONFIRMED`; rejecting (`reject_match`) leaves the Application exactly where it is. A person left with zero Applications after a reassignment is kept (not deleted) — it remains referenced by resolved `PersonMatchCandidate` rows as an audit trail; only its other still-PENDING suggestions (which can no longer resolve to anything) are auto-closed. A direct manual reassignment (`identity_service.reassign_application`, independent of any system suggestion) is also available from the Application detail page.

## 5. Signal Definition configuration UI/service

Task 3C's service layer (`create/update/deactivate/reactivate_signal_definition`) already existed but had no UI. `/signals` now has create/edit/activate-deactivate forms covering every field the task specifies: family, subtype, description, applicable assessment stage(s), allowed evidence source(s), detection guidance, and supporting/contrary/insufficient evidence guidance. Seeded example Signals remain and are editable like any restaurant-authored one. The universal Signal framework (`core/signal_model.py`, `signal_service.py`) still has zero knowledge of any specific restaurant's definitions.

## 6. Review Priority Policy configuration UI/service

`/priority-policies` (list + create) and `/priority-policies/<id>` (rename, activate/deactivate, add/edit/deactivate/remove rules) are new. A rule maps one (Signal Definition, observed status) pair to a qualitative contribution tier — never a number. `ReviewPriorityPolicyRule.is_active` is new; `compute_and_apply_review_priority` only reads active rules, and a deactivated rule stays in place as a record rather than disappearing. Removing a rule is a separate, explicit hard delete. Signal detection code (`signal_detector.py`, `core/signal_model.py`) is untouched by any of this — verified directly (3C-FIX-K: recomputing priority after a policy change never changes the underlying evidence).

## 7. Review Queue behavior

`/applications` now shows candidate/person name, target role, location, application date, source, both system-proposed and effective Review Priority with concise reasons, a repeated-application indicator (prior-application count), current workflow status, an "Open Original CV ↗" link (or a clear "unavailable" label), and a link to the full Application Review. Filter/sort controls (priority, workflow status, target role, application date, repeated-only) are query-param driven; sorting is available, rank positions are not — Applications are never numbered 1..N.

## 8. Application workflow statuses

New: NEW/IN_REVIEW/ADVANCE_TO_PHONE/HOLD/STOP (`core/application_model.py`), persisted on `Application.workflow_status`, defaulting to NEW. `application_service.set_workflow_status()` is the **only** place this field is ever written, and it is called only from the one explicit `/applications/<id>/workflow-status` route — nothing in `signal_service.py` touches it, verified directly (3C-FIX-Q: recomputing Review Priority never changes an already-set workflow status). A reason is accepted (and shown) for any status change, most meaningfully for ADVANCE_TO_PHONE/HOLD/STOP.

## 9. Repeated-applicant/history behavior

Application History already existed (Task 3C); this task adds a facts-only **change-since-prior-application** summary (`core/application_comparison.py`): new role(s) on record, new certification(s), a changed target role, longer relevant tenure toward the current target role, or an explicit "no material professional change detected" line when none of those apply. It never infers motivation/personality from the mere fact of reapplying, and workflow status is never auto-set from it.

## 10. Original CV access behavior

`GET /candidate/<id>/original-cv` streams the exact file `RawResume.storage_path` points to (never a re-rendering of extracted data), restricted to files inside this app's own `uploads/` directory. "Open Original CV ↗" (`target="_blank"`) appears on the Review Queue, the Application Review screen, and the Candidate detail screen. If the row has no `raw_resume_id`, or the file is no longer on disk, a dedicated `original_cv_unavailable.html` page is shown (HTTP 404) instead of a broken link or a 500.

## 11. Notes / decision-reason behavior

New `ApplicationNote` table (append-only) backs a "Selezionatore Notes" section on the Application Review screen with full history and timestamps — replacing Task 3C's single overwritten `Application.notes` field as the primary notes mechanism (that legacy column is kept, untouched, for backward compatibility with the one existing caller in `signal_service.human_confirm_priority`). Notes and workflow-status decision reasons are stored as plain text, never transformed into Signal evidence or used to change a Fit Assessment or Review Priority — verified directly (3C-FIX-S).

## 13. Known limitations directly relevant to Task 3C-FIX

- Name-based matching (STRONG/POSSIBLE) uses simple normalized-string/surname+initial rules — no fuzzy/phonetic matching (e.g. "Jon" vs "John", transposed names) is attempted; this is a deliberate conservative choice (prefer a missed suggestion over a false one), not an oversight.
- Phone normalization strips a leading US/CA "1" country code only; other international formats are matched digit-for-digit as extracted, so genuinely equivalent international numbers in different formats may not match.
- A `CandidatePerson` left with zero Applications after a confirmed reassignment is intentionally kept rather than deleted (see §4) — over time this can leave a small number of empty placeholder person records; nothing currently surfaces or prunes these, since doing so was judged out of this task's scope.
- The Review Queue's filter/sort and repeated-applicant computation are done in Python over the restaurant's full Application list (no pagination) — acceptable at current data volumes, matching every other list view in this MVP, but would need revisiting at much larger scale.
- `sort_by="priority"`/`"status"` sort alphabetically by the category string, not by a defined severity order (e.g. HIGH_PRIORITY does not sort before STANDARD) — a minor UX rough edge, not a ranking (no numeric position is ever shown).
